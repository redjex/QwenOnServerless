завершённый ответ получает 100%, в том числе при раннем окончании.

почти сразу, пока готовится ответ, и раз в 3 секунды в простое; соблюдает

## Синхронизация с облачной машиной

Проект синхронизируется с облачным воркспейсом ML AI Code (https://code.ml.ai)
через публичный GitHub-репозиторий `redjex/QwenOnServerless`. Локальная копия и
облачная машина работают с одной веткой, поэтому изменения видны с обеих сторон.

```sh
npm run sync                  # забрать изменения, закоммитить свои и отправить
npm run sync -- -m "текст"    # со своим текстом коммита
npm run sync -- --pull-only   # только забрать
npm run sync -- --push-only   # только отправить
npm run sync -- --dry-run     # показать план, ничего не меняя
```

Перед отправкой скрипт проверяет изменённые файлы на токены и запрещённые пути
и останавливается, если в коммит попало что-то похожее на ключ. При конфликте
он отменяет прерванный rebase, возвращает локальные правки на место и печатает,
что разрешить вручную; force-push скрипт не делает никогда.

В репозиторий не попадают `.tgcloud/` (токен CLI), `.env`, `node_modules/` и
`models/` — веса занимают 2.5 ГБ. На облачной машине они восстанавливаются
командами из [QWEN.md](QWEN.md): `python scripts/download-qwen.py`,
`python scripts/prepare-qwen.py`, `node scripts/build-kernel.js`,
`node scripts/upload-qwen.js all`.

## Коммиты только с этого компьютера

`main` принимает **только подписанные коммиты**: в настройках репозитория включён
ruleset GitHub «Require signed commits» и запрещён force-push. Закрытый ключ
подписи есть только на этой машине, поэтому писать прямо в `main` может лишь она:
коммиты облачной машины ML AI Code сервер отклоняет. От неё принимаются ветки и
пул-реквесты, а мержит их владелец локально — коммит слияния тоже подпишется:

```sh
git fetch origin
git merge --ff-only origin/<ветка-из-PR>   # или git merge origin/<ветка> для merge-коммита
npm run sync
```

Подпись включается в репозитории один раз. На этой машине она уже включена, на
новом компьютере нужно повторить:

```sh
git config --local gpg.format ssh
git config --local user.signingkey "$HOME/.ssh/id_ed25519.pub"
git config --local commit.gpgsign true
```

и добавить тот же ключ на GitHub: Settings → SSH and GPG keys → New SSH key →
Key type: **Signing Key** (отдельная запись, не путать с ключом для входа по SSH).

## Проверка изменений, присланных облачной машиной

`npm run agent:watch` ловит изменения от агента ML AI Code: смотрит ветки на
`origin` (кроме `main`), а для каждой новой головы запускает проверки в отдельной
временной копии ветки — ваш рабочий каталог при этом не трогается.

```sh
npm run agent:watch                 # все проверки, один проход
npm run agent:watch -- --local-only # без обращения к Telegram
npm run agent:watch -- --watch 60   # проверять каждые 60 секунд
npm run agent:watch -- --branch agent/fix-typo
npm run agent:watch -- --list       # только показать, что нашлось
npm run agent:watch -- --dry-run    # проверить, ничего не отправляя
```

Что проверяется:

| Проверка | Что делает |
|---|---|
| `secret-scan` | изменённые файлы ветки по общим правилам из `scripts/lib/secret-scan.js` |
| `npm-test` | `npm test` в копии ветки |
| `demo` | `npm run demo` — прогон модели, отчёт по шагам и ошибке |
| `telegram-serverless` | реальные вызовы `runtimeCheck` (init → train → read → cleanup) в развёрнутой версии в Telegram |

Вердикт возвращается агенту в песочницу двумя путями: коммитом
`.mlai/verification.json` в его же ветку (читается после `git pull`) и
комментарием к пул-реквесту, если он открыт. Отчёт в ветке подписывается так же,
как всё остальное, и помечается тем же приёмом, что и раньше, поэтому скрипт не
начинает проверять собственный отчёт.

Важно про границы проверки: `npm-test` и `demo` выполняются именно на ветке
агента, а `telegram-serverless` — на **развёрнутой** версии в Telegram. Ветка в
живого бота не публикуется: `tgcloud push` в цикле не вызывается. Локальные
состояния (какие коммиты уже проверены) лежат в `.agent-watch.json`, журнал — в
`.agent-watch.log`; оба файла не попадают в Git.

## Архив первого эксперимента: символьная сеть

Ниже описан предыдущий прототип. Его код сохранён для локальных тестов;
его команды обучения больше не используются опубликованным обработчиком.

Символьная MLP: последние 8 символов → embeddings размерности 16 →
скрытый слой tanh из 64 нейронов → вероятности следующего символа.
Случайные начальные веса, backpropagation, SGD с ограничением нормы градиента.
Готовая модель не загружается. Зависимостей у вычислительного кода нет.

В этой конфигурации алфавит содержит 85 символов, модель — 15 141 параметр.
Веса: 60 564 байта (59,1 КиБ); числовые буферы обучения вместе с весами:
123 004 байта (120,1 КиБ). После демонстрационного обучения JSON checkpoint
занимает около 304 КиБ в UTF-8, его размер зависит от значений весов.

Это учебный генератор коротких текстовых закономерностей. Он не обладает
качествами чат-ассистента, видит только 8 предыдущих символов. Текст приводится
к нижнему регистру; символы вне фиксированного алфавита заменяются на `?`.
Повторяемый демонстрационный корпус проверяет обучение и запоминание,
а не способность обобщать на новые тексты.

## Подключение Telegram

В BotFather создай отдельного тестового бота, включи Serverless,
открой CLI Access и скопируй Access token. Это отдельный токен,
не обычный Bot API token. Вводи его только в интерактивное приглашение CLI.

Из папки проекта:

```sh
npx tgcloud login
```

CLI уже установлен, `tgcloud init` выполнен. Бот подключён, модель развёрнута,
таблица создана, webhook синхронизирован. При переносе проекта на другой
компьютер сначала выполни `npm ci`, а затем `npx tgcloud login`.

Сначала проверь пробу памяти **без развёртывания**:

```sh
npx tgcloud run endpoints/memoryProbe '{mib:1}'
npx tgcloud run endpoints/memoryProbe '{mib:4}'
npx tgcloud run endpoints/memoryProbe '{mib:8}'
npx tgcloud run endpoints/memoryProbe '{mib:16}'
npx tgcloud run endpoints/memoryProbe "{mib:4,kind:'heap'}"
```

Это реальные вызовы среды Telegram, хотя модуль ещё не опубликован.
Не запускай несколько проб одновременно. При необходимости повышай объём
вручную: 32, 64, 96, 128 МиБ, максимум в этом модуле 256 МиБ.
Остановись на первом сбое и сохрани его полный текст. Вариант `typed` проверяет
буферы типизированных массивов, `heap` — обычные JS-массивы чисел.
Учёт этих двух видов памяти платформой может различаться.

`success: true` означает только, что удалось выделить и заполнить указанный
объём числовых данных в данном вызове. У обычных массивов есть дополнительные
накладные расходы, у среды — собственная память. Размер `mib` не равен общему
расходу RAM. Завершение по таймауту не доказывает нехватку памяти; фатальный OOM
может прервать процесс без JSON-ответа. По таким пробам нельзя объявлять
гарантированный официальный лимит.

Затем разверни **только модель, обработчик и схему**, чтобы не публиковать
диагностический endpoint:

```sh
npx tgcloud push tgcloud/schema.js tgcloud/lib tgcloud/handlers
npx tgcloud migrate
```

`npm run deploy` также публикует только модель, обработчик и схему.

В личном чате с ботом:

```text
/start
/stats
/train кот спит. кот ест. кот спит. кот ест. кот спит. кот ест.
/step 128
/generate кот
```

Повторяй `/step 128`, чтобы продолжать обучение; несколько тысяч шагов
достаточны для проверки запоминания такого короткого корпуса. `/train`
заменяет учебный текст, сохраняя веса; `/reset` сбрасывает и веса, и корпус.
Сейчас корпус передаётся текстом сообщения, поэтому дополнительно действует
лимит длины сообщений Telegram. Загрузка текстовых файлов не реализована.

Один вызов делает не больше 128 шагов, генерация — не больше 120 новых символов.
Код дополнительно проверяет мягкий бюджет 100 мс через `Date.now()`, но в
проверенной среде Telegram разница времени внутри синхронных вычислений
возвращала 0. Поэтому основной ограничитель здесь — количество шагов/символов,
а 100 мс нельзя считать гарантированным ограничением длительности.
Это настройки приложения, **не лимит Telegram**. Время вызова проверяй по
выводу CLI. Если платформа не успевает завершить вызов, уменьши число шагов.

Модель и корпус сохраняются отдельно для каждого пользователя в SQLite.
Сохранение проверяет revision: при одновременных командах один результат
будет отклонён, а не затрёт более новое состояние. Повторная доставка одного
Telegram update может дать дополнительную порцию обучения; гарантия
однократной обработки в прототипе не реализована.

## Что известно о памяти

Проверено 24 ноября 2026:

- https://core.telegram.org/bots/serverless
- https://cloud.telegram.org/capabilities

В этих источниках не найден численный лимит RAM/heap/CPU-времени вызова
или квота базы данных. В сторонних публикациях встречается 128 МБ,
но использовать это как подтверждённый лимит нельзя.
Лимит HTTP-ответа 30 МБ и файловые лимиты Bot API не являются лимитами RAM.

Сторонний проект измерений (github.com/DaYzTm/telegram-serverless-limits,
октябрь 2026) и наши замеры дают согласованную картину:

- JS-куча: 127 МиБ проходит, 128 МиБ — `Memory limit exceeded`;
- `ArrayBuffer`/память WebAssembly: 6 ГиБ проходит (наши 325,4 МиБ весов живут
  именно там), значит «512 МБ» — это не лимит RAM;
- CPU на вызов: около 3 000 мс, дальше `CPU timer exceeded`;
- SQLite: около 496 МиБ полезных данных (отсюда и «512 МБ»);
- одновременно платформа держит около 8 вычислительных вызовов.

Это наблюдения на одном боте, а не официальные квоты. Практический вывод:
ёмкость ограничивают база (~496 МиБ) и CPU (~3 с), а не RAM; тяжёлые буферы
надо держать в `WebAssembly.Memory`, а не в JS-куче.

`/stats` показывает размер весов и числовых буферов по `byteLength`.
Дополнительно память нужна для корпуса, JSON, временного массива при
сериализации, SDK и самой среды. JSON checkpoint хранится как текст и
существенно больше двоичных весов. Точная максимальная RAM всего вызова
через документированный SDK недоступна.
