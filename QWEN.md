# Qwen3-0.6B в Telegram Serverless

Эксперимент запускает настоящую предобученную Qwen3-0.6B на инфраструктуре
Telegram. Исходные артефакты: https://huggingface.co/Qwen/Qwen3-0.6B,
лицензия Apache-2.0. Точная ревизия записывается в `models/source.json`
и в манифест, загруженный в базу.

## Уже можно тестировать

Бот: https://t.me/your_bot_username

Отправь `/start`, затем короткий вопрос. Первая часть ответа появится
примерно через 4–5 секунд. Дальше текст дописывается автоматически
в том же сообщении через воркер на сервере `uneed-production` — это единственный
драйвер продолжения. Пока идёт генерация, воркер опрашивает очередь почти
сразу (сотни миллисекунд между вызовами); в простое — раз в 3 секунды.
Ограничения сервиса могут увеличить паузу. Кнопки продолжения нет.
`/stop` останавливает текущий ответ; уже начатая порция может завершиться.
`/last` возвращает снимок последнего ответа, `/stats` показывает
ограничения, `/reset` очищает контекст диалога. Бот помнит последние
сообщения. Новый вопрос заменяет активную генерацию этого пользователя.

## Автоматическое продолжение

Воркер перенесён на `root@uneed-production` и запущен как системная служба.
Локальный процесс остановлен. Компьютер пользователя можно выключать.

- Служба: `qwen-worker.service`, включена в автозапуск и автоматически
  перезапускается при завершении процесса.
- Каталог: `/opt/telegram-qwen-worker`.
- Пользователь службы: `qwen-worker`, без привилегий root.
- Авторизация: `/etc/qwen-worker.env`, владелец root, права 0600.
- Сервисный файл: `/etc/systemd/system/qwen-worker.service`.
- На сервер передан только код оркестрации и зависимости CLI;
  веса и вычисления остались в Telegram.

Команды после подключения по SSH:

```sh
systemctl status qwen-worker --no-pager
journalctl -u qwen-worker -n 50 --no-pager
systemctl restart qwen-worker
systemctl stop qwen-worker
systemctl start qwen-worker
```

Проверено 24 ноября 2026: служба `active/running`, автозапуск `enabled`.
Серверный воркер успешно обработал реальную очередь до 64 выходных токенов.
Развёртывание использует unit из `scripts/qwen-worker.service`.
`scripts/deploy-worker-auth.js` передаёт токен через SSH stdin, получая его
через resolver официального CLI; токен не попадает в архив, аргументы процесса
или вывод команды.

Обновление кода воркера (после правок в `tgcloud/lib/`, `endpoints/qwenPump.js`
или `scripts/qwen-worker.js`):

```sh
node scripts/build-worker-tarball.js
scp models/qwen-worker-deploy.tar.gz root@uneed-production:/tmp/
ssh root@uneed-production "tar -xzf /tmp/qwen-worker-deploy.tar.gz -C /opt/telegram-qwen-worker && cd /opt/telegram-qwen-worker && npm ci && systemctl restart qwen-worker"
```

**`npm run deploy` воркер не обновляет.** `tgcloud run` отправляет все локальные
модули и сервер разрешает импорты только по ним, а не по развёрнутой версии
(`src/commands/run.js` в CLI). Воркер запускает `endpoints/qwenPump` из своего
каталога, поэтому считает **своей** копией `tgcloud/lib`. Если её не пересобрать,
деплой и продолжение работают на разных версиях кода: первая порция ответа
(обработчик в Telegram) — новая, а дописывание (воркер) — старая. Симптом ровно
такой: начало ответа нормальное, продолжение рассыпается.

Установка — **`npm ci` без `--omit=dev`**: сам воркер вызывает официальный CLI,
а `@tgcloud/cli` объявлен в `devDependencies`, и `--omit=dev` удалит его —
служба начнёт падать с `MODULE_NOT_FOUND`.

Архив содержит только файлы бота — без весов и `node_modules`.

Локальный запуск для разработки (сначала останови службу на сервере,
чтобы не запускать две копии одновременно):

```powershell
npm run qwen:worker
```

Процесс `scripts/qwen-worker.js` должен оставаться запущенным на выбранной машине.
Он вызывает `endpoints/qwenPump` через официальный CLI, не читая токены
из `.tgcloud` самостоятельно. Сам вычислитель работает в Telegram.
Локальный запуск не является службой Windows и сам не запускается после
перезагрузки; на сервере за автозапуск отвечает systemd.
При его остановке бот отдаёт только первую порцию, а продолжение
не приходит: VPS — единственный драйвер автодописывания.

`qwenPump` выбирает одну готовую задачу из очереди, запускает очередную
порцию токенов и обновляет исходное сообщение. Поле `auto_enabled` включает очередь только
для новых вопросов после обновления; старые незавершённые ответы не рассылаются
автоматически. `next_run_at` задаёт повторную попытку, lease исключает
одновременную обработку одной генерации. `/stop` отключает очередь, даже если
текущая порция ещё выполняется. Ответ автоматически останавливается при EOS
или после 64 токенов.

Обновление сообщения выполняется под lease до публикации нового checkpoint.
Если доставка не удалась, предыдущий checkpoint остаётся валидным.
Повторное редактирование того же текста безопасно. После трёх обычных ошибок
автопродолжение задачи приостанавливается; ответы `retry_after` учитываются
отдельно. Сам worker соблюдает лимиты CLI и завершается после трёх подряд
обычных сбоев CLI, чтобы не повторять неисправный запуск бесконечно.

PID-файл `models/qwen-worker.lock` предотвращает одновременный запуск двух
локальных процессов. Для остановки в своём терминале нажми Ctrl+C.
Тест очереди без отправки сообщений:

```powershell
node scripts/run-cloud.js endpoints/qwenJob "{action:'start',automatic:true}"
node scripts/qwen-worker.js --once --test
node scripts/run-cloud.js endpoints/qwenJob "{action:'pause'}"
node scripts/qwen-worker.js --once --test
node scripts/run-cloud.js endpoints/qwenJob "{action:'cleanup'}"
```

Этот тест выполнен: worker сам продолжил диагностический ответ с 4 до
8 токенов за 4,87 секунды; после паузы вернул `idle`, не запуская модель.
Тестовая запись удалена. В реальные чаты проверка сообщений не отправляла.

Сейчас модель опубликована, схема применена, webhook принимает `message`
и `callback_query`. Все 236 файлов модели, токенизатора и манифеста загружены:
416,25 МиБ полезных данных. Прогресс можно проверить:

```powershell
python scripts/upload-progress.py
```

Для наблюдения во время повторной загрузки добавь `--watch`.

## Ретранслятор без VPS (два бота)

Продолжение можно вести целиком на Serverless, без VPS, если есть **второй бот**:

- оба бота добавляются в общую **группу**, для обоих выключается privacy mode
  (`/setprivacy` в @BotFather, затем пере-добавить в группу);
- в группе отправляется `/relay` — основной бот запоминает чат (`qwen_meta.relay_group`);
- когда ответ не закончен, основной бот шлёт в группу тик `#qwen-tick user:<id>`,
  второй бот возвращает его эхом, основной получает эхо как апдейт и продолжает;
- боты не получают собственные сообщения, поэтому именно пинг-понг держит цепочку;
- при включённом ретрансляторе `qwenPump` не берёт задачи (`{status:'idle',relay:true}`),
  чтобы VPS и релей не дрались за одну генерацию.

Код: `tgcloud/lib/qwen-relay.js` + проект второго бота в `relay-bot/`
(свой `npm install` и `npx tgcloud login` своим токеном). Настройка — в
`relay-bot/README.md`. Цена: каждый кусок добавляет ~0.5–1 с на круг сообщений.

Разложить **вычисления** по двум ботам (слои 0–13 на одном, 14–27 на другом)
технически можно, но на каждый токен нужен обмен скрытым состоянием через
Telegram — это в разы медленнее, чем посчитать всё в одном вызове. Поэтому
«соединение мощностей» здесь — это релей продолжения, а не разделение модели.

## Как устроен запуск

- Веса берутся из официального BF16 checkpoint. Embeddings преобразуются
  в int8 с одним FP32 масштабом на строку. Матрицы Transformer — в int4
  с отдельным FP32 масштабом для каждой группы из 32 значений.
  Это собственная смешанная конвертация, не GGUF.
- Связанные входные и выходные embeddings хранятся в одной копии; перед
  удалением дубликата конвертер проверяет полное совпадение тензоров.
- Нормализации остаются FP32. KV-кэш, промежуточные результаты и накопление
  матричных произведений также FP32.
- 222 тензорных блока занимают 341 195 624 байта, примерно 325,4 МиБ
  (embeddings в int4). Дополнительно нужны токенизатор (4 411 900 байт), манифест,
  SQLite-индексы.
- База хранит двоичные данные в таблице `qwen_blocks`, кусками до 256 КиБ,
  чтобы укладываться в предел сериализации SDK. `qwen_meta` хранит описания.
- Матричные произведения выполняет небольшое WebAssembly-ядро с SIMD.
  Активации квантуются в int16 и умножаются целочисленным `dot_i16x8`; нормализации,
  RoPE, GQA attention, SwiGLU и токенизатор реализованы на JS.
- Веса загружаются один раз в память ядра по фиксированным смещениям, и matmul
  читает их прямо оттуда — копии матрицы на каждый вызов больше нет. Загрузка
  идёт параллельно, волнами по 8 блоков. Готовый движок кэшируется в области
  модуля: если платформа переиспользует изолят, повторные вызовы не перечитывают
  веса. При `tgcloud run` изолят между вызовами не переиспользуется, поэтому
  каждый вызов заново читает 325,4 МиБ, но уже примерно за 1,6 с вместо 4,2 с.
- После порции генерации KV-кэш записывается в `qwen_kv`, а текст, идентификаторы
  токенов и позиция — в `qwen_generations`. Следующий вызов восстанавливает
  состояние и продолжает тот же ответ. Последний выданный токен ещё не входит
  в сохранённый KV-кэш и обрабатывается первым при продолжении.
- Запись новой версии KV-кэша завершается до публикации состояния; затем
  прежняя версия удаляется. Lease на 120 секунд и revision защищают одну
  генерацию от одновременных нажатий. После аварийного прерывания lease
  истечёт автоматически, а следующая попытка удалит неполные снимки.
- На все KV-снимки введён прикладной бюджет 60 МиБ с учётом временного
  дублирования при сохранении. При параллельном использовании несколькими
  людьми места может не хватить; это экспериментальная версия для теста.
- Внешний API генерации, локальный сервер и GPU для ответа не используются.
  Локальная машина нужна для подготовки и первоначальной загрузки артефактов.

Первая версия бота ограничена 64 входными токенами с учётом шаблона чата,
128 позициями KV-кэша и максимум 64 выходными токенами на ответ.
Один вызов обрабатывает столько выходных токенов, сколько укладывается в
лимит CPU платформы (около 3 с): порция подбирается с запасом, а на новом
вопросе из бюджета вычитается длина промпта, который обрабатывается в том же
вызове. Токен может быть частью слова.
Режим рассуждений отключён официальным шаблоном Qwen3.
Каждый вопрос независим: история диалога, примеры из базы и дообучение
в этом этапе не реализованы.

## Проверка вычислений

`scripts/reference-qwen.py` загружает официальную реализацию Transformers,
применяет ту же смешанную квантизацию и сохраняет эталон в `models/reference.json`.
`scripts/validate-qwen.js` проверяет:

1. Токенизацию русского и английского текста, декодирование и шаблон чата.
2. Выход первого слоя на двух токенах.
3. Выходные оценки полного прохода на 28 слоях и первый токен ответа.

В выполненной локальной проверке:

- токены полностью совпали;
- максимальная ошибка первого слоя: `7.75e-7`;
- максимальная ошибка среди проверенных выходных оценок: `8.11e-6`;
- эталонная генерация на «Привет!» начинается с «Привет! Спасибо за ваше
  приветствие. Можете сформулиров…» (эталон ограничен 24 токенами).

В Telegram проверены:

- первый слой из базы: 2048 значений, около 295 мс (первая int8-проверка);
- полный проход смешанной модели без кэша: первый токен за 4,2 секунды;
- 8 токенов без кэша: 23,4 секунды, около 3,5 ГБ чтения весов;
- 8 токенов с единым WASM-кэшем: 6,1 секунды, веса прочитаны один раз;
- 48 токенов за один вызов не завершились: `CPU timer exceeded`;
- сохранение и восстановление между двумя независимыми вызовами:
  `Привет!` (4 токена, 6,77 с), затем `Привет! Спасибо`
  (8 токенов всего, 5,04 с). Позиция KV-кэша изменилась с 19 на 23.

Сохранение промежуточного текста внутри длинного вызова не устранило
CPU-лимит. Поэтому рабочий бот использует отдельный вызов на каждую порцию,
с автоматическим запуском через worker. Точное численное значение CPU-квоты
не установлено. Проверка через CLI не отправляла сообщений в чаты.

Первоначальная полностью int8-версия не поместилась в базу. После записи
522 051 879 байт двоичных данных очередной INSERT завершился ошибкой
`database or disk is full`. Это объём полезных данных, не официальная квота:
к нему добавляются индексы, служебные страницы и другие таблицы.
Не вместившиеся int8-слои удалены из экспериментальной таблицы, embeddings
сохранены. Итоговая версия использует меньше места благодаря int4-слоям.

## Ускорение, 24 ноября 2026

Изменения в ядре, загрузке и воркере, замеры на платформе через `tgcloud run`:

- загрузка весов: около 4,2 с → 1,6 с (параллельная предзагрузка, волнами по 8
  блоков);
- ядро больше не копирует матрицу на каждый `matmul` — веса лежат в его памяти по
  фиксированным смещениям;
- matmul переписан на целочисленный `i32x4.dot_i16x8`: активации квантуются в
  int16 на лету (точность ~1e-4, эталон проходит: ошибка слоя 2,2e-4, логитов
  0,016 при допуске 0,03, генерация совпадает). Это дало ~1,65× к скорости токена;
- итог по токенам за вызов: было 4, стало **26 надёжно** (34 проходит не всегда,
  44+ упирается в `CPU timer exceeded`; лимит платформы «плавает»). На новом
  вопросе из бюджета вычитается длина промпта, который обрабатывается в том же
  вызове. Бюджет считается в «токен-эквивалентах» (~34 на вызов), prefill дороже
  пропускается через голову только на последнем куске;
- контекст диалога: `qwen_history` хранит последние 8 сообщений; транскрипт
  обрезается до 64 входных токенов, длинный prefill раскладывается на несколько
  вызовов (по ~43 токена), воркер их докручивает. `/reset` очищает контекст;
- частичный текст публикуется каждые 6 токенов, поэтому даже редкий CPU-килл
  оставляет пользователю текст, а не зависшее сообщение;
- движок кэшируется в области модуля: если платформа переиспользует изолят,
  повторные вызовы не перечитывают веса. При `tgcloud run` переиспользования нет
  (проверено: `warmBefore` всегда false), поэтому рассчитывать на это нельзя;
- воркер вместо паузы 20 с продолжает сразу, пока есть прогресс, и ждёт 3 с в
  простое. Распараллелить можно только разные ответы: `--parallel N` запускает
  N одновременных `qwenPump`, платформа держит ~8 вызовов. Внутри одного ответа
  токены распараллелить нельзя — генерация авторегрессивна (N+1 зависит от N);
  для одного пользователя выгоднее `--parallel 1`, иначе лишние линии упираются
  в lease и ждут;
- lease 20 с; если вызов убит по CPU, `qwenPump` снимает протухший lease
  (старше 15 с) и продолжает, а не ждёт две минуты. Новый вопрос всегда
  вытесняет предыдущий ответ (force-acquire), поэтому сообщение «Предыдущая
  порция ещё обрабатывается» больше не появляется. Начальное состояние
  сохраняется до тяжёлого шага — убитый первый вызов подхватывается воркером;

Урезание словаря (`scripts/prune-qwen.js`):

- режим `safe` (по умолчанию) выбрасывает только токены, чьи байты не встречаются
  в латинице/кириллице. Токенизация и качество русского/английского не меняются
  (проверено: генерация совпадает с полной моделью), embeddings падают со 149 до
  101 МиБ, вся модель — с 411,5 до 364 МиБ, доля головы в вычислении токена —
  примерно на треть меньше;
- режим `freq` режет сильнее, но переразбивает промпт и заметно портит ответы
  (проверено — не рекомендуется);
- урезанная модель **загружена в бота**: `vocab_size` 103 034, 26 блоков
  embeddings. Затем embeddings перепакованы в **int4** (`scripts/int4-embeddings.js`):
  101 → 62,9 МиБ, вся модель 411,5 → **325,4 МиБ** (341 195 624 байт). Первый токен
  и 11 токенов ответа совпадают с int8-версией, дальше — синонимичный ход; местами
  int4 даже меньше попугайничает (проверено на двух промптах). Старые блоки и
  «хвосты» удалены (`dropStaleEmbed`, `compact`). Шаг на платформе 3,1–4,7 с.

Контекст и память:

- **KV-кэш перенесён в память WebAssembly** (не в 128 МиБ JS-кучи), поэтому
  контекст ограничен не хипом, а снимком в базе;
- контекст поднят до **256 позиций**, вход — до 160 токенов, ответ — до 64;
  длинный prefill раскладывается на вызовы (~43 токена за раз);
- прикладной бюджет KV поднят до 120 МиБ (база: 325 МиБ весов + до 120 МиБ KV
  ≈ 445 из ~496 МиБ);
- проверено: промпт на 54 токена, prefill 43+11 по вызовам, позиция до 113,
  `bytesRead` 325,4 МиБ.

Вынос весов из SQLite (эксперимент, **не включён**):

- блоки упакованы в 29 документов по ~14 МиБ и отправлены в Telegram
  (`endpoints/qwenFiles` → `pack`); чтение одного файла — ~70 мс в тёплом
  состоянии, ~1,2 с в холодном;
- но загрузка всей модели через `getFileContent` заняла ~15,7 с и вызов
  убивался по `CPU timer exceeded`: доставка содержимого файла дорога по CPU.
  Для загрузки на каждый вызов это в ~4 раза медленнее SQLite (3,7 с), поэтому
  записи `file:*` удалены и бот снова читает из базы;
- механизм оставлен: `scripts/build-bundles.js`, `scripts/upload-files.js`,
  `endpoints/qwenFiles.js` и `readBlock` в `lib/qwen-store.js` (при наличии
  `file:bundle-*` читает из Telegram, иначе из SQLite). Включать имеет смысл
  только если упрёмся в квоту базы, ценой скорости;
- практический вывод: база (~496 МиБ) вмещает урезанную модель (364 МиБ) с
  запасом ~110 МиБ, так что вынос весов сейчас не нужен.
- Побочный эффект эксперимента: в чат владельца отправлено ~30 файлов
  `qwen-bundle-*.bin` и один тестовый блок — их можно удалить вручную.

## Воспроизведение подготовки

Для Python рекомендуется отдельное виртуальное окружение. Нужны PyTorch,
NumPy, safetensors и Transformers 4.57.1. Для WASM — Rust с
`wasm32-unknown-unknown`.

```powershell
python scripts/download-qwen.py
python scripts/prepare-qwen.py
rustup target add wasm32-unknown-unknown
rustc --edition=2021 --target wasm32-unknown-unknown --crate-type cdylib -C opt-level=3 -C target-feature=+simd128 -C panic=abort -C link-arg=--export=__heap_base scripts/qwen-kernel.rs -o models/qwen-kernel.wasm
node scripts/build-kernel.js
python scripts/reference-qwen.py
node scripts/validate-qwen.js
```

Готовое маленькое WASM-ядро включено в `tgcloud/lib/qwen-wasm.js`.
Для обычной работы бота установка Rust и Python не нужна.

## Загрузка весов

После `npx tgcloud login`:

```powershell
npx tgcloud push tgcloud/schema.js
npx tgcloud migrate --safe
node scripts/upload-qwen.js all
node scripts/run-cloud.js endpoints/qwenJob "{action:'start'}"
node scripts/run-cloud.js endpoints/qwenJob "{action:'next'}"
node scripts/run-cloud.js endpoints/qwenJob "{action:'cleanup'}"
```

Загрузчик использует только штатный `tgcloud run`. Он не читает токены
или файлы `.tgcloud` напрямую. Сгенерированные staging-модули передаются
вместе с вызовом, а после загрузки очищаются; в бота они не публикуются.
Модули делятся на части, поскольку платформа ограничивает исходник одного
модуля 1 МиБ.

Локальный `models/packed/uploaded.json` позволяет продолжить прерванную
загрузку. Он относится к текущей базе: при смене бота или удалении данных
нужно убрать этот локальный маркер и повторить загрузку.
Не запускай два загрузчика одновременно: staging-файлы общие.
Загрузчик объединяет записи в пакеты и соблюдает полученный от Telegram
`retry after`, если сервис ограничивает частоту вызовов.

Диагностические endpoints и загрузчик не входят в `npm run deploy`.
